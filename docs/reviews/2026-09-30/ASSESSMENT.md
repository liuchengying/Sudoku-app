# 数独功能、可靠性与交互评估

> 本文是功能完善前的评估存档；缺陷已按后续计划修复，当前实现与验收结果见 [首版记录](../../implementation/2026-09-30/IMPLEMENTATION.md) 与 [无限闯关记录](../../implementation/2026-09-30/INFINITE_CAMPAIGN.md)。本目录的旧诊断用例用于保存当时证据，长期正确行为回归位于 `docs/validation/`。

评估日期：2026-09-30。评估对象为当前工程源码及当前已安装依赖。市场比较采用开发者官网和官方商店介绍，范围为经典单人游戏体验。

## 1. 结论

当前工程已经覆盖离线数独的主要操作和通关闭环，具备继续完善的基础。与成熟产品的主要差距集中在运行可靠性、难度校准、长期题目供给、教学提示和触摸/显示体验。

目前不能将它认定为“已有功能均能顺利运行、交互已经成熟”的版本：类型检查有 10 处错误，默认测试命令在执行用例前失败；隔离配置下核心测试和常规业务流程能够通过，但补充脚本已复现多项实际缺陷。

本次没有启动 H5/App 工程、浏览器、模拟器或用户电脑界面。组件检查在内存中的 Vue 测试宿主执行，不涉及真实页面布局；字体、触摸尺寸和裁切判断属于源码计算或交互设计评估。音效、震动、系统分享、系统返回键、后台/杀进程生命周期和实际屏幕适配仍需后续运行任务验证。

## 2. 当前等级、关卡和积分

当前“等级”实际是难度分组，没有单独的玩家经验等级或晋升体系。

| 难度名称 | ID | 关卡数 | 首次通关积分/关 | 已知数范围 |
| --- | --- | --- | --- | --- |
| 大师 | master | 25 | 2000 | 28～33 |
| 王者 | king | 25 | 4000 | 24～30 |
| 宗师 | grandmaster | 25 | 10000 | 24～31 |
| 合计 | — | 75 | 固定关卡总分上限 400000 | — |

全部关卡可以直接选择；首页无存档时默认显示王者。重复通关可以继续玩并改善成绩，但不重复获得固定积分。“下一关”只递进同一难度，最后一关完成后没有新题供给。

### 难度名称和真实技巧要求尚未充分匹配

本次使用工程内的真实逻辑引擎重新评估全部 75 题：

| 分组 | 仅靠唯一候选/隐藏唯一解完 | 当前逻辑引擎解完 | 当前逻辑引擎停滞 | Core 评分范围 |
| --- | --- | --- | --- | --- |
| 大师 | 25/25 | 25/25 | 0/25 | 64～82 |
| 王者 | 25/25 | 25/25 | 0/25 | 75～107 |
| 宗师 | 0/25 | 7/25 | 18/25 | 98～448 |

据此可以确认，大师和王者在所需技巧上区分不足，部分 Core 评分也有重叠。它们可能在扫描量和步骤数上不同，但不应直接映射为其他产品的专家等级。宗师的 18 道停滞题表示“当前实现的技巧不足以解完”，不表示玩家必须猜数。

JSON 固化的难度分与当前 Core 计算值在 75 题上全部不同；宗师有 21 题的技巧标签与实际求解轨迹/降级标签不同。生成工具的预设标签和评分公式没有与 Core 逻辑评分统一，因此需要校准规则后再确定新等级。

建议用直观的“入门、简单、中等、困难、专家”表达难度，配合技巧要求说明；大师/王者/宗师可以作为称号或高级档位保留。不能只改名称：需补充真正适合初学者的题目，定义各档允许的最高技巧和筛选条件。

## 3. 是否能够无限关卡

**当前不能持续生成新关卡；可以重复玩已有 75 关。工程具备生成器基础，可以扩展为离线持续出题。**

现有 `generatePuzzle()` 能从随机 seed 生成终盘，挖洞时检查唯一解。本次对 3 个 seed × 3 个目标已知数的 9 个对称生成样本进行了唯一解和答案一致性检查，均通过。

生成器目前没有接入首页、游戏模式或题目缓存。仅增加“随机开始”按钮还不足以完成该功能：重新开始、下一关和结算关卡号仍依赖固定题库的 `getLevelById()`，需要让题目来源和模式成为明确的数据。

生成质量还需补足：

- 目标已知数不保证达到。例如 seed=1 的目标 32、28、25 均生成 32 个已知数，不能用目标空格数直接当作难度保障。
- `symmetry:false` 存在实现问题：遍历时仍把镜像位置标记为已访问，却只删除当前格，导致只处理约半盘。本次目标 25 的三个非对称样本实际保留 45、47、47 个已知数。
- 需要唯一解、逻辑可解性、技巧评级、重复题过滤、生成重试/超时和缓存。生成样本通过不代表手机端性能已验证。

推荐产品结构：保留固定关卡供收集奖牌和进度；增加按难度无限练习；增加离线每日挑战及日历/连续完成记录。每日挑战可用本地日期、版本和 seed 确定题目，不必引入后端。随机练习、每日挑战和固定关卡的成绩/积分应分别定义。

这里的“无限”指体验上持续提供新题；标准 9×9 数独题目的数学集合是有限的，产品需要避免短期重复。

## 4. 与成熟产品的功能差异

选择三个比较样本：

- [Brainium Sudoku 官网](https://brainium.com/games/sudoku/)：5 档难度、不限量题目、每日题、逻辑教学提示和撤销重做；[Android 商店介绍](https://play.google.com/store/apps/details?id=com.brainium.sudoku.free&hl=en)还列出数字优先输入、主题/字体调整和横屏。
- [Andoku Sudoku 3 官方商店介绍](https://play.google.com/store/apps/details?id=com.andoku.three.gp&hl=en)：9 档、20000+ 题、离线玩法、逻辑提示、实局教程、书签、自定义题目和变体。
- [Sudoku.com 开发者官网](https://easybrain.com/sudoku)：6 档、数千题、主题、笔记、提示、重复数字高亮、自动检查和每日挑战。

这些是开发者当前公开声明的功能，不能替代对竞品实际操作和所有离线场景的验证。以下建议为结合本项目定位作出的产品判断。

| 维度 | 当前工程 | 差距与建议 |
| --- | --- | --- |
| 基础落子 | 选格后填数、草稿、擦除、候选联动、撤销重做已具备 | 基础覆盖较完整，优先保证边界条件一致 |
| 难度体系 | 三档高级称谓，无初学者档 | 对比上述产品的 5/6/9 档，需增加新手入口并校准技巧等级 |
| 题目供给 | 75 固定题 | Brainium 声明不限量、Andoku 有大题库；增加无限练习更有利于长期使用 |
| 输入效率 | 数字/候选两行均为选格后输入 | 借鉴 Brainium 数字优先连续落子；提供可选输入方式和明确模式标识 |
| 提示 | 一段弹窗说明，选中空格常直接给答案 | 借鉴 Brainium/Andoku 的教学方向，分成区域、技巧、候选排除、答案等逐步提示 |
| 教程 | 静态文字，含部分引擎尚未实现的技巧 | 借鉴 Andoku 的实局教程，增加示例棋盘与操作练习 |
| 检查错误 | 开关式按固化答案即时检查 | 补充手动检查、规则冲突提示和练习/严格模式的计分说明 |
| 显示定制 | 单一浅色主题、固定字体与布局 | 借鉴竞品主题与字体选项，增加深色、大字、清晰对比度和屏幕适配 |
| 长期目标 | 每关奖牌、首次积分、历史 | 每日挑战、完成日历、连续完成记录和本地成就可增加持续目标 |
| 高级工具 | 全盘候选和有限长度复盘 | Andoku 书签可帮助回到分支；可增候选数字高亮、标记和复盘解释 |
| 自定义题目/变体 | 未提供 | 自定义导入可作为后续功能；对角线、不规则等需扩展 Core 约束模型 |

已有优势值得保留：无业务账号依赖、完整本地存档、正确落子同步清理候选、撤销包含候选变化、关卡最佳奖牌、最终棋盘与操作 Timeline。纯离线产品也可以实现上述大部分改进。

### 已确认的问题及优先级

P1 表示应优先修复的错误结果、用户输入受阻或数据不一致；P2 表示影响显示、长期使用或特定场景的问题。

| 编号 | 优先级 | 问题与触发条件 | 证据 |
| --- | --- | --- | --- |
| A01 | P1 | 关闭即时检查后，逻辑提示可能沿错误局面推导出错误数字，并以 `HINT`、`error=false` 填入 | 真实 Store 复现；`game.store.ts` 的 `currentBoard()`、`requestHint()`、`applyHint()` |
| A02 | P1 | 同一模式下，错误数字被数字键当作正确已填数量，导致对应数字键提前禁用 | 真实 NumberPad 渲染及点击事件复现；`NumberPad.vue:19` |
| A03 | P1 | 模拟历史写入失败时，已写入积分、当前局已完成，但历史未写入、当前局存档仍在、跳转未执行 | 真实 Store/Repository 与模拟失败存储；`game.store.ts:440` |
| A04 | P2 | 存储 JSON 能解析但 history.data 是对象时，历史读取直接崩溃 | Repository 复现；`history.repository.ts:29` |
| A05 | P2 | 无 Timeline 的旧历史仍允许滑块从 0 拖到 1，最终棋盘因此变回初盘 | 真实历史详情组件的滑块事件复现；`history/detail.vue:35`、`:78` |
| A06 | P2 | Timeline 超过 1500 条裁掉前置事件，却无对应基线快照，中间复盘缺少已填写格子 | Store 操作 1501 次复现；`game.store.ts:175`、`history/detail.vue:27` |
| A07 | P2 | 历史超过 1000 局时，“累计”局数停止增长，累计时长甚至可能减少 | 历史新增与真实统计 Store 复现；`history.repository.ts:44`、`statistics.store.ts:20` |
| A08 | P2 | 同一奖牌组件从铜升级到金后，颜色更新但内部序号仍为 3 | 真实组件响应更新复现；`MedalBadge.vue:5` |
| A09 | P2 | 非对称生成仍跳过镜像格，目标空格数量无法正常实现 | 生成器源码与 3 个 seed 脚本结果；`generator.ts:89` |

A01 的具体例子：大师第 1 关关闭即时错误检查，第 1 行第 1 列填 7（固化答案为 4）；选中给定数字后请求逻辑提示，系统可将第 1 行第 9 列推导为 9，而其固化答案为 7。测试已确认“一键填入”会保留这个错误数字并标记为非错误。

修复方向：将错误检查展示与内部正确性判定分开；逻辑提示在含错误输入的局面先给出修正引导；结算采用可重试、可恢复的整体提交；存储增加结构校验；历史裁切保存基线；累计统计独立于历史保留；奖牌序号改为响应式派生。

## 6. UI 与人机交互评估

### 已有的友好设计

- 选中格、同行/列/宫、同数字均有高亮，给定数字不可修改。
- 草稿模式有视觉状态；暂停有遮挡及“点击继续”。
- 替换当前局、重开、退出和清空进度有确认提示。
- 首页能继续当前局，通关能重玩或进入下一关，关键操作有文字标签。

### 源码可见的改善点

| 问题 | 当前表现或计算 | 建议 |
| --- | --- | --- |
| 首次使用门槛 | 默认王者；三档均为高级称谓；只有文字玩法文章 | 首次推荐入门，提供可跳过的选格/填数/笔记练习，保留直达游戏入口 |
| 输入模式理解 | 蓝色一行是候选，灰色一行是答案；切草稿后下排也变为候选 | 明确“填写/笔记”状态，提供简洁单键盘及可选双排布局 |
| 连续输入效率 | 每次都要选格再按数，无数字优先连填 | 提供锁定数字后连续点格模式，笔记同样适用 |
| 候选可读性 | 375 CSS px 宽度按源码换算，候选字体约 8.5px | 大字/放大棋盘选项、候选字重与对比度调整；在真实设备确认最终尺寸 |
| 数字键触摸区 | 同宽度换算约 38.33×43 CSS px | 优先扩大数字键和工具触摸区；允许适合单手的布局选项 |
| 字色过浅 | `#929399/白` 对比约 3.06:1；`#b0b2b6/白` 约 2.12:1；可选关卡数字约 1.57:1 | 提升关键说明与可选关卡的对比度，降低“像被禁用”的视觉误导 |
| 小屏首页网格 | 断点 swiper 高度 720rpx；5 行格子、间距、内边距和边框至少需 754rpx | 让容器随内容计算高度，或明确提供纵向滚动/分页，避免末行裁切 |
| 小屏游戏页 | `disableScroll:true`，棋盘和输入区主要尺寸固定，未基于可用高度整体计算 | 按可用高度分配棋盘/工具/输入区，覆盖小屏、安全区和系统大字体 |
| 提示过快揭晓 | 选中空格时通常直接返回该格答案；弹窗包含答案且请求即计数 | 区域→技巧→候选排除→答案的逐级提示，展示目标格与依据，提前说明计数规则 |
| 暂停与菜单状态 | 打开更多即暂停，关闭后仍暂停；暂停时工具仍能点击但 Store 拒绝 | 根据打开前状态恢复或明确保持暂停，禁用不可用工具并避免误导反馈 |
| 检查与引导 | 关闭即时错误后没有手动检查入口；没有独立行/列/宫冲突反馈 | 加入手动检查及“检查正确性/只检查规则冲突”的明确选项 |
| 进度表达 | 关卡网格之外，下一目标和完成比例不突出 | 显示难度完成数、推荐下一未完成关，增加未完成/已完成筛选 |
| 长历史性能 | 历史页一次渲染全部卡片，1000 局可包含 81000 个数字格节点 | 分页或窗口化展示，卡片缩略图按需渲染；性能结论需实机测量 |

对比度采用源码颜色计算；普通文字 4.5:1、大文字 3:1 可参考 [W3C Contrast Minimum](https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum)。这里不是完整合规审计，装饰文字和禁用元素需要按用途分别判断；当前关卡均可选，其数字不属于已禁用元素。

Android 建议交互区域至少 48×48dp，并为控件提供可理解的语义，见 [Android 官方可访问性指导](https://developer.android.com/guide/topics/ui/accessibility/views/apps-views)。本次计算值为 CSS px，不能直接当作真机 dp 测量结果；应以它们作为适配复核线索。可选补充格子行/列/值/候选的读屏描述，以及不只依赖颜色的错误/提示状态。

## 7. 建议实施顺序与验收重点

### 第一轮：可靠性与基础体验

修复类型检查和默认测试配置、A01～A08，并处理小屏容器、数字键和低对比度。验收包括：错误检查开关切换后辅助逻辑一致；存储失败后能够恢复并且不重复发分；各类历史滑块/复盘正确；奖牌升级即时更新；主操作在不同可用高度下均可到达。

将本次“复现错误行为”的诊断用例改为正确行为的回归断言后，再合并为长期测试。当前诊断文件使用 `.cases.ts`，只由评估配置显式执行，不自动混入默认 `*.spec.ts` 用例集合。

### 第二轮：题目体系和长期可玩性

定义入门到专家的技巧等级；统一题库评分；修复 A09；让题目来源独立于固定 ID；接入离线无限练习并明确生成预算、重试、重复过滤和缓存。验收应覆盖随机局存档/恢复/重开/结算，选定难度与实际技巧匹配，以及手机端生成等待和中断行为。

### 第三轮：教学与操作效率

实现分步教学提示、实局练习、数字优先模式、手动检查、深色/大字设置、候选数字高亮。验收应确认提示不会直接破坏练习目的、模式切换不易误填、关键状态可辨认。
